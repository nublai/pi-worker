# A0 slice 1 on pi-durable 1.5.2 — THROWAWAY comparison

**Status: Complete for this comparison, not Gate 1, production, or a migration. Recommendation: stay with pi-coding-agent RPC/SDK; borrow Durable's transactional admission and committed-state views.** Durable successfully owns a conversation behind the existing CLI, but its automatic recovery contradicts the current unknown/fence policy, does not contain orphaned tools, and does not load the coding-agent ecosystem. Restart-surviving approvals are possible with released primitives and application code; they are not a turnkey feature.

No decision or production change is required. Reconsider adoption only if automatic continuation and durable approvals become explicit product requirements, their authority/cleanup semantics are agreed, ecosystem ports are funded, and API stability improves.

## What was built

- **`src/durable-main.ts`**: second entry point, restricted scratch state under `/tmp/a0d/`, private Unix socket, host-owned single-writer lock, JSONL `fsync:true`, explicit CodingTools and NodeExecutionEnv, `resume()` after mounting recovered conversations. SIGTERM closes the Harness and releases its lock; SIGKILL deliberately exercises recovery. No changes to Pi/herdr configuration.
- **`src/durable-host.ts`**: creates a conversation per worker; preserves worker binding IDs; maps durable conversation/submission IDs to B2 strings. App-owned control document stores serialized worker metadata and final receipts, **not prompt values**. Input content remains in Durable's transcript/inbox. `submit(tx, ...)` and receipt persistence are atomic. Reusing native requestId with different content is NOT a native conflict check: our existing canonical request hash supplies that rule.
- **Same B2 surface**: `src/cli.ts` and `src/client.ts` unchanged; router accepts either host and awaits history. OpenAPI adds only `durable_storage` and `durable_conversation_id` evidence labels rather than falsely calling SQLite/JSONL a supervisor journal or coding-agent session file. Types regenerated.
- **Views**: Durable's conversation watch feeds the existing EventHub/SSE barrier and `durable_view` events. The B2 snapshot still contains its existing Worker/history projection, **not a full Durable view/partial-answer snapshot**. Live events include the native view/ops; EventHub stubs payloads above 16 KiB. A real UI would need a deliberate bounded view projection. `agent_settled` is a compatibility **adapter event from `pi.live.run` removal**, not coding-agent's native event. Failed/aborted runs also become idle; inspect `runFailure`, not an event name, to decide success.
- **History**: pages raw Durable entries with a pinned watermark. Entry IDs are numeric in native entries, stringified in B2 cursors; IDs are storage-local, not global Pi session UUIDs. Stock Pi cannot open this transcript as a coding-agent session. Full byte caps, invalid-cursor hardening, branches and large-history stress remain absent in this adapter.
- **Stop**: aborts the conversation including background tasks and then records stopped. It reports `durable_tasks_idle` with OS descendants `unproven`, never observed process termination. Abort and its final control receipt are **not atomic**; a crash between them leaves the stop command outcome unrecorded. This is a named spike limitation, not a solved receipt implementation.

`hello` advertises these differences, no contract conformance, same-user access, machine-loss limits, unbounded prototype receipt retention, no interaction endpoints, and the automatic resume policy. We kept default `npm start` on RPC; `npm run start:durable` selects the experiment.

### Recovery results and contract invariants

**Real mid-model:** the authored [real crash driver](evidence/durable-real-crash.mjs) attaches a native watch and waits for actual text, not echoed prompt content or a pre-dispatch marker. It SIGKILLs the process, reopens the same fsynced JSONL, reuses the requestId, and explicitly calls `resume()`. A beforeRequest hook counts two attempts in different processes; a real partial before the kill and a final real answer after restart corroborate dispatch. No tools were enabled in this probe. The first partial did not reach durable storage before the kill, so the recovered history has no aborted assistant entry; this illustrates the documented deferred-progress window, not a lost user submission. [Evidence](evidence/durable/real-model-crash.json).

**Deterministic mid-model plus queue:** first process entered `MODEL_CUT`; `QUEUED_INPUT` was admitted while busy; host SIGKILL; new host explicitly called `resume()`. Evidence has two `MODEL_CUT` factory calls in different PIDs and one queued call. Original command lookup and duplicate submission retain the exact admission receipt. Transcript has one user entry for each command, each answered. No fence appears.

The first request was cut before its first persisted partial, so no aborted assistant entry is claimed. Released docs/source explain retry budgets/backoff, interrupted partial retention, and `runFailure: interrupted` when retry is exhausted. This test uses two allowed retries and a 100 ms base delay. It does **not** test exhaustion; under the default failed-run policy, queued inputs can remain waiting after a run fails instead of draining automatically.

**Mid-bash:** built-in bash appended exactly `ONCE\n`, published `BASH_STARTED`, and waited six seconds before writing `FINISHED\n`. The driver read the actual start file before killing the host. After reopening, the transcript contains diagnostic **`interrupted`: "Tool bash was interrupted and may have partially run"**. The faux model consumed that result and then answered `AFTER_BASH_QUEUE`. Start count stayed one, but the **old shell** wrote its finish marker after the resumed turn. That is surviving execution, not replay. All these finite tools finished or were aborted; final process scan found no owned live probes/hosts/MCP server.

This confirms the base Fix round's cleanup lesson: neither RPC process groups nor Durable task abort are a containment boundary. Durable does not persist and reconcile NodeExecutionEnv child identities as the contract's cleanup barrier requires. The adapter makes no descendant-cleanup claim.

### Approvals: a useful released capability, with limits

The authored approval fixture uses **only 1.5.2**: session-scoped `defineDoc`, `beforeTool`, commits, `watchDoc`, ordinary input `requestId`, and `resume()`. It persists a pending description/binding (`artifact: fixture-v1`, `policy:1`, task ID), waits in the hook, then is killed. Reopening finds the same pending document and same tool task; the hook is entered a second time. An explicit fixture `approve` command commits the decision; only then does `execute()` append one effect. The native input also remains one submission.

This is **application reconstruction of a wait**, not persistence of the JavaScript Promise. `beforeTool` has not yet crossed the tool-execution intent checkpoint, so its call phase can rerun. The fixture holds an invocation/watch while waiting; it is not a hibernation-ready parked approval service. A document by itself does not suspend a task or authenticate a person.

Important source detail: recovery of an **already-intended replay-safe tool** enters the `execute` phase, which does **not re-run beforeTool**. A production gate must revalidate current grants, artifact/policy/expiry/revocation immediately at effect release, including replay, rather than treating one earlier hook result as perpetual permission. Our fixture has no authenticated actor, expiry, revocation, concurrent-answer protocol, answer-stage receipts or sandbox. None is claimed proven.

Current contract §5 explicitly says pending interactions die. Preserving the card above would require a product/contract change and new interaction generations/answer semantics. Alternatively, application policy could mark the persisted pending document interrupted on startup. **No `defineSignal`, typed signal delivery, or main-branch ask-a-person API is present or used.** The released README/hooks and `dist/harness/tool.js:38–140` are the evidence.

## Borrow, do not misattribute

**Worth borrowing now:**

1. **One transaction for admission + caller metadata.** `submit(tx)` rollback test stores neither submission nor receipt. Eliminates an avoidable journal-vs-runtime dual-write gap where the runtime is owned in-process. On RPC, retain conservative dispatch uncertainty instead of pretending to have that atomicity.
2. **Committed-state views, bounded transcript windows and snapshot replacement.** Native partials/tool slots/queue/failure are explicit state. Keep transport epoch/barrier and slow-client bounds; do not call deferred partials fsynced. Default progress can lose about one second.
3. **Separate submission outcome, run failure and tool uncertainty.** Final admission receipts need not be rewritten after a crash. Keep execution evidence and controls distinct, as the base Fix round already does.
4. **Explicit unsafe/safe tool replay and durable inbox.** Useful design vocabulary, but only replay external effects with their own idempotency, and never use interrupted-tool output as permission to ignore a session fence.
5. **Document-backed approval identity and bindings.** Makes stale intent visible and reconstructible. Its lifetime is a policy choice; approval authority still belongs to the control plane/gate, not the conversation scheduler.

**Not solved:** authenticated B2 grants, answer-stage proofs, escaped process cleanup, global worker/environment identity, exactly-once external effects, job acceptance/verification, workspace durability, or stock Pi/Herdr compatibility. Conversation durability, job durability and workspace durability stay separate owners (§0.0).

## Recommendation and decision triggers

**Stay RPC/SDK for A0.** Use SDK when native resolver ownership is the requirement; do not migrate merely to get a durable queue or a named tool-interruption result. Preserve the explicit unknown latch and require real process containment before automatic continuation can be safe for side-effecting coding work.

Reconsider Durable if (1) automatic mid-run resume or restart-surviving approvals are approved requirements, (2) the revised contract explicitly defines interrupted effects, queue release and gate revalidation, (3) containment and writer ownership are demonstrated, (4) coding-agent/Herdr ecosystem parity is delivered or consciously dropped, and (5) two minor releases establish acceptable API/storage stability. A **hybrid** may use Durable for an isolated application-owned orchestration/approval service while keeping coding-agent workers, but must not create competing owners for jobs, receipts or approval outcomes; that hybrid was not built or validated here.
